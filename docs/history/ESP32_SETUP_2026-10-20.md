### Proposed wire contract for a later verified capture producer

Little-endian32-byte header: `struct <4sBBHIIQII`.

| Field | Size | Meaning |
|---|---:|---|
| magic |4| ASCII SNC1 |
| version |1|1 |
| type |1|1=status,2=JPEG |
| flags |2| must be0 |
| boot/session ID |4| new ID after producer restart |
| sequence |4| unsigned frame sequence, modulo2^32 |
| capture counter |8| device-relative microseconds, not UTC |
| payload length |4|1..2048 for status,1..131072 for JPEG |
| CRC32 |4| zlib CRC32 of the first28 header bytes followed by payload |

Type1 payload is bounded JSON: `role:"camera_capture"`, `device_id` matching the inspected physical camera, `init_status:"ready"` or an actual error, and a sensor-driver-read integer `sensor_pid` for ready status. No specific PID is assumed. Frames from another session, without initialized status, with invalid PID/CRC/JPEG, replayed sequence or regressing capture counter are rejected. Initialization errors may arrive before any JPEG and must remain visible. Firmware logs/legacy telemetry must stay outside this dedicated stream; type1 is camera status, not host telemetry. The current primary telemetry firmware is not this producer or relay.

At1152008N1 the theoretical payload ceiling is11520 bytes/s before framing/overhead. A10KiB JPEG alone needs about0.89 seconds;128KiB needs about11.4 seconds. The parser/source uses a15-second deadline and a128KiB frame cap. These are design bounds, **not measured camera performance**. Actual sensor resolution, quality, RAM budget and rate cannot be selected responsibly before the actual board/sensor and initialization are verified.

### ROM transport requirements and chosen host handoff

ESP32 ROM traffic is binary SLIP, not text or JSON: bytes0x00..0xFF, 0xC0 delimiters and 0xDB escapes must pass unchanged. Both physical UART links are fixed at 115200 baud,8N1; no hardware flow control is assumed. No telemetry, logging, newline translation or escape sequence is added in raw mode.

The chosen route is:
esptool raw localhost TCP -> one host relay -> DevKit UART0 via CH9102 -> DevKit UART2 TX17/RX16 -> camera UART0.

The relay constructs a closed pyserial port, sets DTR=False and RTS=False before open, opens it once, verifies the bridge firmware, and keeps it open until shutdown. Esptool connects to a raw TCP endpoint instead of reopening COM9. TCP control requests cannot toggle the DevKit reset lines. OS/driver glitches on initial open are still possible; a successful idle handshake is required before enabling UART2. No physical proof of glitch-free opening exists yet.

This is raw TCP, not RFC2217. Client baud changes cannot reconfigure either UART; do not request higher baud or issue a ROM baud-change command. Future diagnostic esptool use must retain its default115200 (no environment/config override) and use --before no-reset --after no-reset. Do not use no-reset-no-sync for a newly reset ROM target: synchronization is required. A --no-stub chip-id check is a read-only first diagnostic after all physical gates pass, not a flash.

Inspected installed host esptool:5.6.0. Its socket-port logic selects no-reset, and pyserial socket transport does not propagate UART control settings. PlatformIO build tooling independently uses esptool5.4.0. Neither tool installation was changed.

Sources: [Espressif raw socket serial ports](https://docs.espressif.com/projects/esptool/en/latest/esp32/remote-serial-ports.html), [reset options](https://docs.espressif.com/projects/esptool/en/latest/esp32/esptool/advanced-options.html), [boot-mode controls](https://docs.espressif.com/projects/esptool/en/latest/esp32/advanced-topics/boot-mode-selection.html), [Arduino UART API](https://docs.espressif.com/projects/arduino-esp32/en/latest/api/serial.html).

### Firmware and host control behavior

- On DevKit start, GPIO16/17 are inputs and UART2 is off. No target IO0/EN/reset pin is configured.
- BRIDGE.STATUS returns identifying settings. Only the idle state accepts the exact arming line BRIDGE.ARM POWER_VERIFIED BOOT_VERIFIED. These words are operator declarations, not electrical measurements.
- The host additionally requires explicit declarations that power and boot controls are verified and that the camera is in download mode. Without --serve it does not open a serial port or listen on TCP. With missing declarations it fails before opening serial.
- The host binds127.0.0.1 only, accepts one client and arms UART2 only after acceptance. There is no external network listener or persistent service.
- After the complete raw-mode ACK, all bytes are opaque in both directions. Partial writes remain buffered, and text resembling control commands remains payload. No in-band stop command is safe for arbitrary binary data.
- Firmware stops UART2 after30 seconds without host bytes, even if camera output continues. A15-minute absolute session bound and UART receive-error handling also stop forwarding. It restores GPIO16/17 as inputs and latches locked, rejecting re-arm until a DevKit reset. It emits no unsolicited stop text into raw traffic.
- Host limits are10 seconds without traffic,10 minutes total relay time,60 seconds waiting for a local client, and bounded writes/control reads. Long erase/read operations may need a separately reviewed timeout choice; none was physically validated.
- On session end or a lost ARM reply, the host stops transmitting, drains replies for approximately32 seconds, then requires a locked status. Until that shutdown is confirmed, camera power must not be removed while DevKit TX may still be driven. If the host is killed or USB disappears, confirmed shutdown is unavailable; do not infer an electrically safe state solely from the host exiting.
- A transport disconnect/byte count is not successful esptool synchronization or flashing. User must not press DevKit BOOT/EN during a future camera operation: resetting it into its own ROM would invalidate the transport assumption and could address the wrong chip. Future target identity must be checked against the known DevKit before any write.
